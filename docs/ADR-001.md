# ADR-001 — Explicit ack только после коммита локальной транзакции

## Контекст

Платформа публикует и потребляет события через JetStream (at-least-once). Производитель
пишет событие в transactional outbox в одной PostgreSQL-транзакции с бизнес-изменением
(feasibility, правило 2), relay публикует его в JetStream, consumer ведёт inbox-запись
(feasibility, правило 3). Вопрос: в какой момент consumer подтверждает (ack) сообщение?

Исходный Ensi использовал Kafka auto-commit (feasibility: «в исследованной конфигурации
Ensi включён Kafka auto-commit»). PRD-033 требует доказать порядок «commit → ack»
(FR-006, BDD-033#S-10) и отсутствие потерь/дублей при сбое между коммитом и ack
(FR-007, BDD-033#S-11).

## Варианты

1. **Auto-commit (Kafka-вариант Ensi).** Consumer подтверждает сообщение сразу после
   получения, до обработки. При сбое процесса между commit и завершением бизнес-
   транзакции сообщение потеряно — at-least-once нарушен. Быстро, но именно та потеря,
   которую PRD-033 явно запрещает (G-3: «сбой между коммитом и ack не теряет и не
   дублирует событие»).
2. **Outbox + explicit ack после COMMIT (предлагается).** Consumer: BEGIN →
   idempotency-insert в inbox → бизнес-обработка → COMMIT → ACK в JetStream.
   Сбой между коммитом и ack → JetStream redelivery → inbox-constraint отсекает дубль
   (FR-002, FR-007). At-least-once + идемпотентность.
3. **Ack до коммита (ack-first).** Ускоряет consumer, но сбой после ack до COMMIT
   теряет событие навсегда — несовместимо с G-3, отвергнуто.
4. **Транзакционный outbox только на стороне продюсера + fire-and-forget ack.**
   То же, что вариант 1 для consumer: потеря в окне до обработки. Отвергнуто.

## Решение

Выбран вариант 2: **explicit ack отправляется в JetStream только после COMMIT
локальной транзакции PostgreSQL** (порядок commit → ack, FR-006/BDD-033#S-10).
Обработка сообщения: idempotency-insert + бизнес-обработка + commit в одной транзакции,
затем ack; при ошибке обработки — nack (redelivery по `AckWait`, FR-004). Гарантии
at-least-once достигаются комбинацией outbox (продюсер) + inbox-constraint (консьюмер) +
explicit ack после COMMIT. Соответствует feasibility, правило 4.

## Последствия

**Положительные:**
- Сбой между коммитом и ack не теряет и не дублирует событие: redelivery отсекается
  уникальным `inbox_events.event_id` (FR-007, BDD-033#S-11);
- дубль `Nats-Msg-Id` не доходит до бизнес-обработчика (FR-002, BDD-033#S-3, S-5);
- поведение проверяемо тестом с fault injection «crash after commit, before ack»
  (BDD-033#S-11, PRD-033 Q-2).

**Отрицательные / принятые риски:**
- Дублирующаяся доставка после сбоя между COMMIT и ACK (окно теряется): безопасно
  благодаря idempotency, но увеличивает latency и число запросов к БД при сбоях;
- обязательный порядок commit → ack требует дисциплины библиотеки: ack нельзя
  делегировать фоновой горутине до COMMIT (защита — код-ревью + тест S-10, фиксирующий
  порядок операций);
- в отличие от auto-commit, при зависании транзакции сообщение не будет подтверждено
  до `AckWait` — redelivery может слегка дублировать обработку при долгих транзакциях
  (компенсируется идемпотентностью).

## Миграция клиентов

Не применимо: решение затрагивает только поведение библиотеки на этапе foundation
(PRD-033), публичный контракт outbox/inbox ещё не создан.
